# 표준 요건과 산출물 대응

이 표는 심사/평가에서 "어떤 요건을 어떻게 만족했는가"를 설명할 때 쓴다. 조항 번호는 버전에 따라 다르므로 보고서에는 적용한 버전을 함께 적는다.

## Automotive SPICE

| 프로세스 | 버전 | 관련 요건(요지) | 이 스킬에서 만족하는 방법 |
|---|---|---|---|
| SWE.6 Software Qualification Test | 3.1 | 테스트 명세 개발(테스트 케이스 포함), 테스트 케이스 선정, 테스트 명세 ↔ SW 요구사항 양방향 추적성, 일관성 보장 | 기능/비기능 시트 = 테스트 명세, `테스트 베이시스 ID` 열 + 추적성 매트릭스 시트 = 양방향 추적성, 스크립트 검증 = 일관성 |
| SWE.6 Software Verification | 4.0 | 검증 수단(verification measure) 명세(합격 기준 포함), 검증 수단 선정, 양방향 추적성과 일관성 | `예상 출력값` = 합격 기준, `사용한 테스트 기법` = 도출 근거, 추적성 매트릭스 |
| SYS.5 System Qualification Test / System Verification | 3.1 / 4.0 | 위와 같으며 대상이 시스템 요구사항 | 베이시스가 시스템 요구사항일 때 같은 산출물 구조 사용 |

추적성 요건의 핵심은 **양방향**이다.
- 정방향: 요구사항 → 테스트 케이스. 추적성 매트릭스에서 모든 요구사항에 TC가 있다.
- 역방향: 테스트 케이스 → 요구사항. 모든 TC에 실재하는 베이시스 ID가 있다.

`build_workbook.py`는 양쪽을 모두 검사한다.

## ISO 26262-6:2018 — Clause 11 "Testing of the embedded software"

| 요건(요지) | 이 스킬에서 만족하는 방법 |
|---|---|
| 테스트 환경 선택(HIL, ECU 네트워크, 차량 등. Table 13) | 사전 조건에 환경을 적는다. 사용자가 지정하지 않으면 HIL을 가정하고 보고서에 적는다 |
| 테스트 방법: 요구사항 기반 테스트(1a), 결함 주입 테스트(1b) (Table 14) | `요구사항 기반 테스트`, `결함 주입` 기법 표기. ASIL 요구사항과 안전 메커니즘에는 결함 주입을 검토한다 |
| 테스트 케이스 도출 방법: 요구사항 분석(1a), 동치 클래스 생성/분석(1b), 경계값 분석(1c), 경험·지식 기반 오류 추측(1d) (Table 15) | 동치 클래스·경계값 분석 필수 적용. WoW 검증 케이스는 오류 추측 성격의 엣지 케이스 |
| 각 방법의 권장 수준은 ASIL에 따라 다름(ASIL C/D에서 대부분 highly recommended) | ASIL C/D 항목은 1a–1d 모두 적용했는지 확인하고, 적용하지 않았으면 `technique_notes`에 근거를 남긴다 |
| SW 안전 요구사항에 대한 요구사항 커버리지 | 커버리지 요약 시트의 베이시스 커버리지 100% |

ISO 26262-6 Clause 9(SW unit verification)와 Clause 10(SW integration verification)은 이 스킬의 범위가 아니다. 구조 커버리지(문장/분기/MC/DC)는 단위 시험의 지표이므로 이 스킬의 "커버리지"는 **테스트 베이시스 커버리지**를 뜻한다.

## 표준 문구 사용 시 주의

표준 원문을 인용할 때는 사용자가 가진 표준 문서로 확인한다. 이 표는 요지이며 원문 번역이 아니다.
