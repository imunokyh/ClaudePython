# 테스트 설계 기법 적용 가이드

예시 요구사항(이 문서 전체에서 사용):
> SWR-010: 차속(VehSpd, 0–250 km/h, 분해능 1 km/h)이 15 km/h 이상이 되면 500 ms 이내에 전 도어를 잠근다(DoorLockCmd = LOCK).

## 1. 동치 클래스 (Equivalence Partitioning)

1. 각 입력의 도메인을 **같은 동작을 유발하는 구간**으로 나눈다. 유효 클래스(요구사항이 정의한 동작)와 무효 클래스(범위 밖, 잘못된 형식, 신호 무효)를 모두 본다.
2. 클래스마다 대표값 하나로 케이스를 만든다.
3. 유효 클래스는 한 케이스에 여러 개를 묶어도 된다. 무효 클래스는 한 케이스에 하나만 넣는다.

예: VehSpd
- EC1 유효: 0–14 km/h (잠금 안 함)
- EC2 유효: 15–250 km/h (잠금)
- EC3 무효: >250 km/h 또는 신호 무효(Invalid/Timeout). 요구사항에 처리가 정의되지 않았으면 `제안` 케이스로 만들고 질의 사항에 올린다.

## 2. 경계값 분석 (Boundary Value Analysis)

1. 순서 있는 도메인의 각 경계에서 **경계값과 분해능 ±1** 값을 고른다(3-값 BVA). 2-값 BVA를 쓰려면 이유를 `technique_notes`에 적는다.
2. 경계는 입력 범위의 끝, 임계값, 타이머, 카운터, 히스테리시스 양쪽 경계다.
3. 시간 요구사항(500 ms 이내)도 경계다. 합격 기준이 "≤ 500 ms"이면 측정값이 경계 안인지 판정하는 비기능 케이스가 된다.

예: 임계값 15 km/h → 14, 15, 16 km/h. 상한 250 → 249, 250, 251(251은 무효 클래스와 겸함).

동치 클래스 대표값을 경계값과 겹치게 골라도 된다(예: EC2 대표값 = 15). 이때 `techniques`에 두 기법을 모두 적는다. 케이스 수를 줄이면서 두 기법을 모두 만족하는 정당한 방법이다.

## 3. 페어와이즈 (PICT)

**적용 조건**: 서로 독립적인 입력 파라미터가 3개 이상이고, 각각 2개 이상의 값(보통 동치 클래스 대표값)을 가지며, 조합에 따라 동작이 달라질 수 있을 때. 파라미터가 2개면 전수 조합을 쓴다(페어와이즈가 의미 없음).

**모델 파일** (`PICT-01.pict.txt`):
```
IgnState: OFF, ACC, ON
Gear: P, R, N, D
VehSpd: 0, 14, 15, 120
DoorOpen: CLOSED, OPEN

IF [IgnState] = "OFF" THEN [VehSpd] = 0;
IF [Gear] = "P" THEN [VehSpd] = 0;
```
- 값은 동치 클래스 대표값과 경계값에서 가져온다. 임의의 값을 넣지 않는다.
- 물리적으로 불가능한 조합은 제약(constraint)으로 제거한다. 그대로 두면 실행할 수 없는 케이스가 생긴다.
- 무효값은 `~` 접두어(예: `~INVALID`)로 표시하면 PICT가 한 행에 무효값 하나만 넣는다.
- 파라미터 이름과 값은 영문/숫자로 쓴다. 한글은 PICT 콘솔 인코딩 문제로 깨질 수 있다.

**실행**: `python scripts/run_pict.py PICT-01.pict.txt --id PICT-01 --out PICT-01.json`(기본 2-way. 필요하면 `--order 3`).

**케이스화**: PICT 결과의 각 행이 케이스 하나다. 각 행의 예상 출력값은 요구사항으로 직접 계산한다. 결정할 수 없는 행이 있으면 모델(제약)을 고친다. TC의 `pict_ref`에 `PICT-01#3`처럼 모델 ID와 행 번호를 적는다.

## 4. WoW 검증 (엣지 케이스)

정상 경로와 단일 경계로는 드러나지 않는 **극단적·복합적 상황**을 검증한다. 기법 표기는 반드시 `WoW 검증`이다. 후보:

| 유형 | 예 (SWR-010) |
|---|---|
| 경계에서의 진동 | VehSpd가 14↔15를 100 ms 주기로 반복할 때 잠금 명령이 반복 송신되지 않는가 |
| 타이밍 경계 | 15 km/h 도달 직후 499 ms 시점에 도어가 열리면? |
| 동시 이벤트 | 15 km/h 도달과 동시에 수동 잠금 해제 입력 |
| 신호 소실/복귀 | 20 km/h 주행 중 VehSpd 신호 타임아웃 후 복귀 |
| 초기화/전원 | 15 km/h 이상에서 ECU 리셋 직후 첫 주기 |
| 극단값 | 최대값 250 km/h, 0→250 급변 |
| 상태 이력 | 이미 LOCK 상태에서 다시 조건이 충족될 때 |

규칙:
- 요구사항에서 기대 동작을 도출할 수 있으면 `기본`, 가정이 필요하면 `제안`으로 표시하고 가정을 사전 조건이나 비고에 적는다.
- "있을 수 있다" 수준의 시나리오는 넣지 않는다. 실제 차량/시스템에서 발생할 수 있는 상황만 넣는다.

## 5. 결함 주입 (ISO 26262-6 Table 14 1b)

ASIL 요구사항, 안전 메커니즘(감시, 타임아웃, CRC/Alive counter, 안전 상태 전환)에 적용한다. 주입 대상(신호 무효, CRC 오류, 카운터 정지, 전원 강하), 주입 방법(HIL 결함 주입 기능), 기대 안전 반응과 반응 시간(FTTI 이내)을 적는다. 대부분 비기능 시트에 들어간다.

## 6. 요구사항 기반 테스트

입력 도메인이 없는 단순 이벤트-응답 요구사항에 쓴다. 이 경우 동치 클래스와 경계값 분석이 적용되지 않는 이유(예: "입력 파라미터 없음")를 `technique_notes`에 적는다.
