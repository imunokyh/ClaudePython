# SW 시스템 테스트 케이스 생성

요구사항 문서(테스트 베이시스)를 받아 **실행 가능한** 테스트 케이스를 설계하고, 검증 스크립트를 통과한 엑셀 파일로 납품한다.

이 스킬의 결과물은 A-SPICE 심사나 ISO 26262 기능안전 평가에서 증적(work product)으로 쓰인다. 그래서 "그럴듯한 표"가 아니라 다음을 만족해야 한다:
- 모든 테스트 베이시스 항목이 최소 1개의 의미 있는 테스트 케이스로 검증된다 (커버리지 100%).
- 모든 테스트 케이스가 근거가 되는 베이시스 ID를 가진다 (양방향 추적성 100%).
- 각 케이스에 적용한 설계 기법이 명시되어, 심사원이 "이 케이스는 왜 이 값인가"를 따라갈 수 있다.
- 시험자가 추가 질문 없이 HIL/벤치에서 그대로 수행할 수 있다.

표준 요건과 이 스킬 산출물의 대응은 `references/standards.md`, 기법별 상세 적용법은 `references/techniques.md`에 있다. 처음 사용할 때 두 파일을 모두 읽는다.

## 도구

- `scripts/run_pict.py` — PICT 실행 래퍼. 모델 파일을 받아 조합 결과를 JSON으로 저장한다.
- `scripts/build_workbook.py` — 테스트 케이스 JSON을 검증하고 엑셀로 만든다. 추적성·커버리지·필수 항목·기법 적용 오류가 있으면 엑셀을 만들지 않고 오류를 출력한다.

둘 다 `python <스킬경로>/scripts/<이름>.py --help`로 사용법을 볼 수 있다. PICT는 GitHub `microsoft/pict` 릴리스의 `pict.exe`를 쓴다. PATH, `PICT_PATH` 환경 변수, `%LOCALAPPDATA%\Programs\pict\pict.exe` 순서로 찾는다. 없으면 사용자에게 설치를 요청한다. 페어와이즈 조합을 손으로 만들어 PICT 결과인 것처럼 쓰면 안 된다. 증적이 위조되기 때문이다.

## 작업 흐름

### 1. 입력 확인

- **테스트 베이시스**: 요구사항 문서(Word, Excel, PDF, Markdown, 텍스트 무엇이든). 없으면 요청한다. 추측해서 만들지 않습니다.
- **테스트 케이스 양식**: 사용자가 엑셀 양식을 주면 그 양식을 쓴다(아래 5단계의 `template`). 없으면 기본 양식을 쓴다.
- **테스트 레벨**: 베이시스가 SW 요구사항이면 SWE.6(SW 자격 시험), 시스템 요구사항이면 SYS.5(시스템 자격 시험)로 본다. 분명하지 않으면 SWE.6로 가정하고 보고서에 적는다.
- **ASIL**: 요구사항에 ASIL이 있으면 기록한다. ASIL 요구사항은 결함 주입(fault injection) 케이스가 필요한지 판단하는 근거가 된다.

### 2. 테스트 베이시스 분해

요구사항을 **검증 가능한 최소 단위**로 나누고 각 항목에 ID를 붙인다.
- 원문에 ID가 있으면 그대로 쓴다. 한 ID에 독립적으로 검증할 조건이 여러 개면 `SWR-010.a`, `SWR-010.b`처럼 나누고 원 ID와의 관계를 남긴다.
- ID가 없으면 `TB-001`부터 부여하고, 보고서에 "ID 임의 부여"라고 적는다.
- 각 항목을 `기능` 또는 `비기능`으로 분류한다. 비기능: 응답 시간·주기·지연 등 타이밍, 메모리·CPU 부하 등 자원, 견고성·오류 처리·결함 주입, 시동/리셋/전원 등 운용 조건, 진단 성능 등.
- **검증 불가능한 요구사항**(기대값 없음, "적절히", "빠르게" 등 모호함, 서로 모순)은 테스트 케이스로 덮지 말고 `issues`에 질의 사항으로 남긴다. 추정 기대값으로 케이스를 만들면 커버리지는 채워져도 틀린 합격 기준이 증적에 남는다. 합리적 가정으로 진행할 때는 케이스에 가정을 명시하고 `제안`으로 표시한다.

### 3. 테스트 설계 (항목마다)

각 베이시스 항목에 대해 입력·출력 파라미터, 단위, 범위, 분해능(resolution), 상태(state), 타이밍을 뽑은 다음, 아래 기법을 적용한다. 상세 규칙과 예시는 `references/techniques.md`에 있다.

| 기법 | 적용 | 표기 |
|---|---|---|
| 동치 클래스 | 필수. 입력 파라미터가 있는 모든 항목에 적용. 유효·무효 클래스 각각 | `동치 클래스` |
| 경계값 분석 | 필수. 순서가 있는 범위/임계값/타이머가 있는 모든 항목에 적용. 분해능 단위로 경계 ±1 | `경계값 분석` |
| 페어와이즈 | 독립 파라미터가 3개 이상이고 조합 상호작용이 의미 있을 때. PICT로 도출 | `페어와이즈(PICT)` |
| WoW 검증 | 엣지 케이스: 동시 이벤트, 상태 전이 경계, 타이밍 경계, 신호 소실/복귀, 초기화 직후, 극단값 조합 등 | `WoW 검증` |
| 요구사항 기반 | 위 기법이 해당되지 않는 단순 기능(이벤트→동작) | `요구사항 기반 테스트` |
| 결함 주입 | ASIL 요구사항의 안전 메커니즘, 오류 처리 요구사항 | `결함 주입` |

입력 파라미터가 없어서 동치 클래스나 경계값 분석이 성립하지 않는 항목도 있다(예: "시동 시 버전 정보를 송신한다"). 이런 항목은 억지로 기법을 붙이지 말고 `technique_notes`에 적용하지 않은 이유를 적는다. 스크립트는 이유 없이 빠진 경우만 오류로 본다.

### 4. 쓰레기 케이스 걸러내기

케이스를 확정하기 전에 각 케이스마다 묻는다: **"이 케이스가 잡을 수 있고, 다른 케이스는 못 잡는 결함은 무엇인가?"** 답이 없으면 지우거나 합친다.

- 동치 클래스 대표값과 경계값이 같은 동작을 검증하면, 경계값 케이스가 대표값 역할을 겸할 수 있다. 같은 클래스에 값만 바꾼 케이스를 늘리지 않는다.
- 커버리지를 위해 베이시스 ID만 다르고 내용이 같은 케이스를 복제하지 않는다. 한 케이스가 여러 항목을 실제로 검증하면 `basis_ids`에 모두 적는다.
- 무효 클래스는 한 케이스에 하나씩만 넣는다. 여러 개를 섞으면 어느 것 때문에 거부됐는지 알 수 없다.

### 5. 실행 가능성 기준

각 케이스는 아래를 모두 만족해야 한다. 하나라도 빠지면 시험자가 판단해야 하므로 재현성이 깨진다.
- **사전 조건**: 시스템 상태, 모드, 전원/점화 상태, 초기 신호값.
- **입력값**: 신호/변수 이름, 구체적인 값, 단위. "유효한 값", "큰 값" 같은 표현은 쓰지 않는다.
- **절차**: 순서 있는 단계. 타이밍이 중요하면 시간을 적는다(예: "2단계 후 100 ms 이내").
- **예상 출력값**: 관측 가능한 신호/상태와 구체적인 값, 허용 오차, 판정 시점. "정상 동작한다"는 금지한다.

### 6. 제안 케이스

베이시스가 직접 요구하지 않지만 결함 위험이 있다고 판단해 추가하는 케이스(요구사항 공백, 명시되지 않은 무효 입력 처리, 가정에 기반한 엣지 등)는 `origin: "제안"`으로 표시하고, 가장 가까운 베이시스 ID를 추적 대상으로 단다. 엑셀의 `구분` 열에 "제안"으로 나온다. 베이시스에서 바로 도출된 케이스는 `origin: "기본"`이다.

### 7. JSON 작성 → 검증 → 엑셀

1. 페어와이즈가 필요하면 PICT 모델 파일(`*.pict.txt`)을 만들고 실행한다:
   ```
   python <스킬경로>/scripts/run_pict.py <모델파일> --id PICT-01 --out <작업폴더>/PICT-01.json
   ```
   PICT 행마다 케이스를 만들고, 각 행의 예상 출력값은 요구사항으로 직접 계산한다. 결과 JSON을 `pict_models`에 넣는다.
2. 테스트 케이스 JSON을 작성한다. 스키마는 `references/json_schema.md`에 있다.
3. 검증하고 엑셀을 만든다:
   ```
   python <스킬경로>/scripts/build_workbook.py <tc.json> --out <결과.xlsx>
   ```
   오류가 나오면 JSON을 고쳐서 통과할 때까지 반복한다. 오류를 피하려고 의미 없는 케이스를 추가하지 않는다. 4단계 원칙이 우선이다.

### 8. 보고

사용자에게 다음을 짧게 알린다.
- 엑셀 경로와 시트 구성: 기능 테스트 / 비기능 테스트 / 추적성 매트릭스 / 커버리지 요약 / PICT 모델(있을 때) / 질의 사항(있을 때)
- 베이시스 항목 수, 커버리지 %, 케이스 수(기능/비기능, 기본/제안), 기법별 케이스 수
- 질의 사항과 가정. 사용자가 확인해야 하므로 빠뜨리지 않는다.
